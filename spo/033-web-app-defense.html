Защита веб-приложения: самостоятельное изменение функции и объяснение кода

Защищайте свой VariantNN-web, который вы проверяли на предыдущей практике. На защите покажите работающий сценарий, самостоятельно измените поведение одной JavaScript-функции, а затем докажите двумя испытаниями, что правка дала ожидаемый результат и сохранила знакомое действие.

Содержание

  • Исходное состояние
  • Самостоятельная правка
  • Проверка правки
  • Показ и объяснение
  • Резервный маршрут

1. Подготовьте исходное состояние

  1. Откройте репозиторий в GitHub Desktop, свою папку в редакторе и работающий сайт в браузере. Для проверки правки откройте сайт на localhost из этой же папки. Если сервер ещё не запущен, воспользуйтесь инструкцией по локальному запуску. Запишите текущий адрес и номер версии.
  2. Откройте в редакторе расчётную функцию в скрипте формы или функцию поиска в скрипте каталога. Найдите строку, из которой она вызывается. Подготовьте обычный пример со своего варианта: позиция и количество для формы либо запрос и ожидаемое число карточек для каталога.
  3. Повторите один сценарий прошлого занятия. Например, введите запрос, обновите страницу и покажите, какие карточки остались. При готовом кеше полезно сразу повторить этот шаг в F12 → Application → Service Workers → Offline. После опыта снимите Offline перед изменением кода.

2. Получите условие и измените функцию

На защите преподаватель задаёт одно условие для имеющейся функции. Ниже приведены примеры такого задания. Названия и данные берите из своего проекта.

Где менять Пример требования Чем проверить
Функция расчёта Принимать количество до 10 включительно. При большем количестве выводить понятное сообщение без суммы На 10 получается итог по прежней формуле, на 11 — отказ
Функция поиска Для непустого запроса искать совпадение только в начале названия. Пустой запрос показывает весь каталог Начало названия находит карточку, его середина, которой нет в начале названий, её не находит, пустой запрос восстанавливает все карточки
  1. Прочитайте условие. Назовите файл и функцию. Найдите её входные данные, ветку, которую потребуется изменить, и место, где результат выводится на странице.
  2. До редактирования запишите минимум два примера: меняющийся случай и обычный случай, который должен по-прежнему работать. В таблице выше для расчёта меняется поведение на 11, а при 10 сохраняется действующая формула. Для поиска можно добавить отдельный опыт с пустым запросом.
  3. Покажите исходное поведение на меняющемся вводе. Самостоятельно внесите изменение в функцию и сохраните файл. Перед защитой можно использовать свои конспекты и прежние статьи для подготовки. Саму правку на показе выполняйте по выданному условию и объясняйте написанные строки.

С чего начать

Если меняете расчёт, проследите путь от строки из поля через проверку и вычисление до текста в #result. Если меняете поиск, проследите, как строка становится условием отбора и как список попадает в функцию отрисовки. Это поможет найти место правки и выбрать ввод, на котором её результат виден.

3. Проверьте результат и сохраните правку

  1. Обновите локальную страницу и повторите оба испытания. Для расчёта проверьте ещё одно неверное количество, если исходная функция его уже отклоняла. Для поиска, если он сохранялся, обновите страницу с запросом и проверьте, что применилось новое правило к восстановленному тексту.
  2. Если всё выглядит как до правки, проверьте путь подключения скрипта, сохранение файла и ошибки в Console. Если включён кеш, для быстрой проверки кода на локальном адресе при выключенном Offline временно включите Application → Service Workers → Bypass for network и обновите страницу. После проверки снимите эту галочку. Такое испытание подтверждает результат новой функции при загрузке с сервера.
  3. Чтобы повторить испытание новой функции автономно, измените номер VERSION и видимую подпись версии, обновите регистрацию и дождитесь активации, как в предыдущей практике. С выключенной галочкой Bypass for network включите Offline, перезагрузите страницу и повторите меняющийся случай. Если времени на активацию обновления не хватило, отдельно назовите версию, которую реально видели без сети.
  4. В GitHub Desktop → Changes покажите строки, относящиеся к заданию. Сделайте локальный коммит с кратким названием правки и запишите его имя. Для защиты достаточно локального коммита. Выключите Offline по окончании.

4. Покажите проект и объясните код

Проведите показ на своём компьютере. Держите рядом браузер, редактор и GitHub Desktop.

  1. Назовите назначение приложения и покажите путь пользователя: главная, каталог, форма. В одном месте выполните действие и назовите ожидаемый результат.
  2. Покажите самостоятельное изменение и оба испытания. Объясните, откуда функция берёт вход, какое условие изменилось, что функция возвращает и где пользователь видит результат. В истории покажите локальный коммит.
  3. Покажите восстановление запроса или иной проверенный автономный сценарий после Ctrl + R в режиме Offline. Назовите проверенную версию. Объясните, какую роль играет service worker и где браузер хранит значение, которое пережило перезагрузку.

Что должно быть видно при защите

По одному вводу видно новое поведение, по другому — сохранённое обычное действие. В коде видна строка или ветка, которая даёт это различие. Результат проверки без сети относится к тому адресу и той версии, которые вы открыли при показе.

5. Проведите защиту без телефона или интернета

Без телефона выполните все действия на компьютере. Режим Offline в инструментах браузера позволяет показать повторную загрузку с кешем. Если внешней сети нет, используйте локальный сервер на localhost и локальную историю Git. Файлы кешируются при первом обращении к работающему локальному серверу с выключенным Offline.

Если ни локальный, ни опубликованный сервер не открывается, покажите правку и локальную историю, назовите свои тестовые входы и вручную проследите ход функции по коду. Если сохранилась ранее проверенная автономная версия, покажите её отдельно с номером. Зафиксируйте, какие испытания новой версии ожидают запуска.
