Настройка PWA и проверка установки, автономной работы и обновления

Продолжайте свой VariantNN-web. На первой паре вы готовили первую версию с sw.js и размещали её через GitHub Pages. Теперь проверьте, какую версию открывают браузер и установленное приложение. К концу занятия покажите, что новая версия открывается без сети, а обновление файлов сохранило настройку поиска.

1. Проверьте исходное состояние

  1. Для проверки на телефоне возьмите HTTPS-адрес приложения из Settings → Pages. Сначала откройте его на ПК. Сверьте успешное размещение коммита в Actions и номер первой рабочей версии в sw.js по адресу сайта. Если готовы только папка на ПК, коммит или репозиторий, вернитесь к стартовой проверке GitHub и шагу 5 в статье первой пары.
  2. Для опыта обновления выберите один адрес и профиль браузера на ПК. В DevTools откройте Application → Service Workers и убедитесь, что sw.js контролирует страницу. В Cache Storage найдите рабочий кеш. Если HTTPS-адрес пока недоступен, выполните опыт на localhost. Если номер уже менялся, используйте последний рабочий номер вместо v1 и следующий номер вместо v2.
  3. В Application → Manifest проверьте название, значки, стартовую страницу и область приложения. Сверьте их с настройкой манифеста. Начальный адрес должен открываться и входить в набор первой пары. Если добавляете недостающие файлы в уже активный кеш, делайте это через новую версию sw.js, затем принимайте её как рабочую основу испытания.
  4. Откройте каталог и введите запрос, дающий известный результат. Перезагрузите страницу и проверьте поле, карточки и счётчик. Если запрос уже сейчас не восстанавливается, зафиксируйте исходное наблюдение: обновление кеша само не добавляет эту возможность.

2. Проверьте установку и запуск без сети

Когда переходить к телефону

По ссылке GitHub Pages на ПК открываются главная, каталог и форма, браузер читает манифест и значки, а sw.js управляет страницей. Перенесите на телефон именно эту HTTPS-ссылку. localhost на телефоне обращается к самому телефону. Если доступен только локальный запуск, проверьте автономность на ПК и отметьте, на каком шаге остановилась публикация.

На компьютере или телефоне откройте адрес проекта в обычном браузере. Найдите в меню доступную команду установки или добавления на главный экран. Запустите приложение из созданного значка и проверьте, где оно открылось, как называется и куда ведёт первый экран. В Chrome и Edge пункты меню могут различаться. Если доступен только ярлык, зафиксируйте его фактическое поведение. Если команды нет, запишите браузер и наблюдение и продолжите проверку во вкладке компьютера.

Телефон сначала должен увидеть приложение онлайн

Кеш с компьютера на телефон не переносится. На телефоне откройте этот же сайт с сетью, дайте ему загрузиться и перезагрузите страницу обычным способом. Перед отключением сети проверьте, что открываются главная, каталог и форма.

Проверка Действие и ожидаемый результат
Повторная загрузка на ПК Включите Offline в DevTools для проверяемой вкладки и нажмите Ctrl + R. Открываются страницы из кеша, работает CSS
Действие без сети По ссылкам приложения откройте каталог и форму, измените запрос и проверьте счётчик, сделайте локальный расчёт формы
Холодный запуск на телефоне при наличии Закройте окно приложения, отключите Wi‑Fi и мобильные данные, заново запустите его из значка. Открывается стартовый экран, можно перейти в каталог и форму
Возврат сети Выключите симуляцию Offline, на телефоне восстановите подключение

Если телефон не доступен, результат на компьютере подтверждает автономную работу в браузере этого компьютера. Телефонную установку и запуск оставьте непроверенными.

3. Выпустите следующую версию и найдите её в браузере

Проводите этот опыт на компьютере, на том же адресе и в том же профиле. Отображение ожидающего worker зависит от открытых страниц, поэтому оставьте две вкладки проекта. Если приложение установлено, его отдельное окно тоже может контролироваться старой версией.

  1. Запомните любую видимую подпись на главной странице рабочей версии. В index.html замените её на Учебная версия 2 и сохраните файл. Если номер версии уже выше, подставьте номер своего нового выпуска.
  2. В sw.js замените текущий номер версии на следующий. Список ресурсов и прежний идентификатор приложения из манифеста сохраните. Если часть файлов нужно добавить для испытания, проверьте их адреса заранее. На GitHub Pages разместите HTML и sw.js одним коммитом. В GitHub Desktop проверьте их в Changes, нажмите Commit to … → Push origin, затем найдите этот коммит в ветке размещения и дождитесь успешного запуска в Actions. По HTTPS-адресу sw.js проверьте новый номер. На localhost достаточно сохранить файлы.
  3. Убедитесь, что в DevTools выключены Update on reload и Bypass for network. В одной вкладке откройте Application → Service Workers и нажмите Update при работающей сети. Если кнопка недоступна, обычная перезагрузка тоже может запустить проверку. Вторая вкладка остаётся открытой под управлением старой версии.
  4. Проверьте в DevTools, что новый worker установлен и ждёт (waiting или waiting to activate). Посмотрите оба кеша. Обновите главную обычным способом, пока другая вкладка открыта: старый worker должен показать прежнюю подпись. Если нового worker нет, проверьте в Network ответ для sw.js, его версию и сообщения установки. При ошибке получения ресурса ищите неуспешный адрес в списке FILES.
  5. Закройте обе вкладки проекта и все окна установленного приложения для этого сайта в том же профиле. Через несколько секунд снова откройте главную по прежнему адресу. Проверьте новую подпись и кеш новой версии. Старый кеш проекта после активации должен исчезнуть.
  6. Проверьте ранее сохранённый запрос каталога и соответствие поля, карточек и счётчика. Включите Offline и ещё раз загрузите главную. Она должна показать новую подпись. Откройте каталог и убедитесь, что фильтр работает. После проверки восстановите сеть.

Проверяйте обычное обновление

Для перехода между версиями не очищайте данные сайта и не удаляйте регистрацию. Это уберёт свидетельства обновления и может удалить поисковый запрос. Перезагружайте страницу обычным сочетанием Ctrl + R, без принудительного обхода кеша.

4. Разберите результат, если проверка не прошла

Наблюдение С чего начать
На GitHub есть файлы, но по ссылке приложение не открывается Скопируйте адрес сайта из Settings → Pages, проверьте ветку, корневой index.html и результат запуска в Actions
Манифест виден, команды установки нет Проверьте HTTPS, загрузку значков, сообщение панели Manifest и возможности текущего браузера
Страница без сети открывается частично Сверьте точные адреса CSS, JS, изображений и других зависимостей с содержимым кеша
Кеша новой версии нет или он пуст Проверьте, был ли получен новый sw.js, затем найдите ошибку install. Один обязательный адрес с ответом 404 останавливает заполнение
Новый worker всё ещё ждёт Проверьте другие вкладки и окно установленного приложения в том же профиле. Закройте все управляемые страницы проекта
Кеш новой версии есть, подпись старая Уточните, какой worker активен, что реально содержится в записи index.html нового кеша и были ли HTML и sw.js развернуты вместе
Подпись обновилась, запрос исчез Проверьте профиль, происхождение (схему, домен и порт), ключ localStorage и код восстановления. На другом устройстве локальные значения отдельные

Что показать преподавателю

Покажите стартовую страницу с новой подписью, кеш новой версии и повторное открытие без сети. Покажите действие в каталоге и коротко объясните, что увидели при установке и во время ожидания обновления. Если отдельный этап недоступен, назовите браузер, устройство и наблюдаемую причину. Отдельный отчёт готовить не нужно.
